## 1) Purpose

هذا النظام هو طبقة التشغيل والحوكمة فوق النماذج، الأدوات، الذاكرة، والـ workflows.
هدفه تقليل العشوائية، رفع الثبات، تسريع التنفيذ، ومنع اعتماد مخرجات غير مراجعة.

---

## 2) Execution Order

الترتيب الافتراضي لأي مهمة:

1. فهم الطلب
2. استرجاع السياق والذاكرة عند الحاجة
3. قراءة محلية للمشروع
4. استخدام الفهم الدلالي إذا لزم
5. اختيار النموذج المناسب
6. تنفيذ التعديل أو التحليل
7. التحقق الإلزامي حسب حجم المهمة
8. تقطير ما يستحق إلى الذاكرة

**الصيغة المختصرة:**  
`Context → Read → LSP → Model → Execute → Verify → Distill`

> **بروتوكول التحديثات أثناء التنفيذ:** بعد 3-5 استدعاءات أدوات متتالية بدون رد على المستخدم، أرسل تحديثاً. للعمليات المتوقعة > 30 ثانية، أخبر المستخدم قبل البدء. انظر CLAUDE.md — "بروتوكول التحديثات".

## 3) Model Routing Policy

### النموذج الأساسي: `deepseek-v4-flash[1m]` (افتراضي — بلا تثبيت)

النموذج الافتراضي لكل جلسة هو `deepseek-v4-flash[1m]` عبر `model: sonnet`. `env.ANTHROPIC_MODEL` **محذوف**، فلا تثبيت — والتصعيد عبر `/model` حرّ في أي وقت.

### الحرية الكاملة في الاختيار

- `/model sonnet` → `deepseek-v4-flash[1m]` (الأساسي)
- `/model opus` → `deepseek-v4-pro[1m]` (تصعيد للمهام المعقدة)
- `/model haiku` → `deepseek-v4-flash[1m]`
- التبديل يعمل أثناء الجلسة وبين الجلسات، بلا تعديل ملفات.

### صعّد إلى `deepseek-v4-pro[1m]` عندما:

- تتطلب المهمة reasoning عميقًا أو تخطيطًا طويلًا
- المهمة وكيلية متعددة الخطوات أو معمارية/حساسة
- الحاجة لدقة أعلى في البرمجة أو التحليل
- الاستدعاء: `/model opus` أو طلب فئة opus من وكيل
- عند المهام المعقدة، **ينبّه الوكيل المستخدم للتصعيد** إن لم يكن قد صعّد مسبقًا

### لماذا Flash أساسي؟

- اقتصادي للمهام التافهة (تلخيص، ترجمة، بحث بسيط) التي لا تحتاج reasoning
- تحكم كامل: المستخدم يصعّد يدويًا متى شاء
- تذكير: إن كانت أغلب مشاريعك معقدة (أطر حديثة، قواعد بيانات، تطبيقات متعددة المنصات) فلا تتردد في التصعيد على المهام الثقيلة

### الإعدادات الحالية

```json
{
  "model": "sonnet",
  "ANTHROPIC_DEFAULT_OPUS_MODEL": "deepseek-v4-pro[1m]",
  "ANTHROPIC_DEFAULT_SONNET_MODEL": "deepseek-v4-flash[1m]",
  "ANTHROPIC_DEFAULT_HAIKU_MODEL": "deepseek-v4-flash[1m]",
  "CLAUDE_CODE_EFFORT_LEVEL": "high"
}
```

> ⚠️ **ملاحظة:** `env.ANTHROPIC_MODEL` محذوف عمدًا — وجوده يثبّت نموذجًا ويتجاوز `/model`. حذفه هو ما يمنح حرية التبديل. أسماء الفتحات توافقية مع واجهة Anthropic ولا تعكس النموذج الفعلي.

### طبقات التصعيد

- الجلسة الرئيسية: Flash (الافتراضي) · التصعيد اليدوي: Pro عبر `/model opus` بقرار المستخدم · الوكلاء الفرعيون: كلهم Flash (sonnet). التفاصيل الكاملة في CLAUDE.md — «توجيه النموذج والتصعيد».

## 4) Provider Bridge / Gateway Policy

### المبدأ

إذا كانت Claude Code تعمل مباشرة مع Anthropic، فلا تحتاج هذه الطبقة.
أما إذا كانت تستخدم DeepSeek أو مزودًا آخر عبر Claude Code، فيجب توثيق gateway بوضوح.

### الإعدادات الحالية

```md
Provider Mode: Gateway
Gateway: DeepSeek API (Anthropic-compatible endpoint)
ANTHROPIC_BASE_URL: https://api.deepseek.com/anthropic (via settings.json)
Credential Type: ANTHROPIC_AUTH_TOKEN
Credential Location: متغير بيئة ANTHROPIC_AUTH_TOKEN؛ وأثناء تسجيل الدخول عبر `claude` يُخزَّن مشفّراً في `.auth.sec` (Windows DPAPI) — وليس في settings.json (الذي لا يحوي أي سر)
Upstream Provider: DeepSeek
Upstream Models:

- deepseek-v4-flash[1m] (الأساسي)
- deepseek-v4-pro[1m] (تصعيد للمهام المعقدة)

Capability Status:

- Messages API: full
- Tool calling: full
- MCP: partial — GitHub/Playwright/Supabase/Context7/SeqThinking ✅, Vercel/Flutter/VideoVision ⚠️ (الاتصالات الخارجية لا تمر عبر gateway)
- Streaming: full

### Fallback: MCP الضعيفة عبر gateway

بعض MCP تحتاج اتصالات خارجية مباشرة لا تمر عبر gateway. **عند فشلها — لا تتوقف، انتقل للبديل:**

| MCP ضعيف عبر gateway          | البديل المحلي/الآمن           |
| ----------------------------- | ----------------------------- |
| Vercel (`mcp__plugin_vercel`) | CLI `vercel` المحلي (مثبت ✓)  |
| Flutter (`mcp__plugin_vgv`)   | CLI `flutter` + `very_good`   |
| VideoVision                   | WebFetch مباشر (لا بديل محلي) |

**القاعدة:** عند فشل أداة MCP عبر gateway → استخدم CLI المحلي أو WebFetch، ثم سجّل نمط الفشل في الذاكرة (failure-pattern). لا تتوقف عن المهمة بسبب فشل MCP.

Notes:

- القيم مخزنة في settings.json ولا تُتلف في التوثيق
- أسماء النماذج هي aliases منطقية للمزود النهائي (DeepSeek)
- لا توجد limitations معروفة مقارنة بـ Anthropic native حالياً (تحقّق 2026-08-17 على 2.1.233: WebSearch وWebFetch وsubagents تعمل)
- عيوب تكامل تاريخية نُشرت على 2.1.166 وزالت على 2.1.233: تعارض `thinking:disabled`+`reasoning_effort` (يكسر الوكلاء)، تجميد مصنّف الأمان لـ Bash، رفض `tool_choice` (يكسر WebSearch/WebFetch). التفاصيل في ذاكرة [[deepseek-v4-integration-bugs]]
```

## 5) Tool Routing Policy

### القاعدة الأساسية

ابدأ دائمًا بأبسط أداة تحقق الهدف بأقل تكلفة.

### ترتيب الأدوات

1. الذاكرة والسياق
2. `Read` / `Glob` / `Grep`
3. `LSP`
4. `Edit` / `Write`
5. `Skill`
6. `Agent`
7. `Workflow`
8. Web / MCP عند الحاجة الفعلية فقط

### متى تستخدم كل طبقة؟

| الطبقة                   | الاستخدام                                                   |
| ------------------------ | ----------------------------------------------------------- |
| `Read` / `Glob` / `Grep` | بحث عن ملفات أو نصوص أو دوال، وفهم أولي سريع                |
| `LSP`                    | تتبع التعريفات والمراجع، rename، refactor، وفهم دلالي       |
| `Edit` / `Write`         | `Edit` للتعديل الدقيق، و`Write` للإنشاء أو الاستبدال الكامل |
| `Skill`                  | نمط متكرر أو checklist أو أسلوب موحد                        |
| `Agent`                  | مهام متعددة الخطوات أو قابلة للتفويض                        |
| `Workflow`               | تحقق أو pipeline متعدد المراحل                              |
| Web / MCP                | فقط عند عدم كفاية السياق المحلي أو الحاجة الفعلية           |

### قواعد المنع

- لا تستخدم `Agent` لمهمة صغيرة
- لا تستخدم `Workflow` لمهمة مباشرة
- لا تستخدم Web أو MCP قبل استنفاد السياق المحلي
- لا تصعّد الأدوات لمجرد الحذر أو الاستعراض

## 6) Memory Operating Rules

### المبدأ

الذاكرة ليست لتخزين كل شيء، بل لتخزين ما يؤثر على القرارات المستقبلية.

### ما يُحفظ

- قرارات معمارية أو تقنية مؤثرة
- تفضيلات المستخدم الثابتة
- الأخطاء المتكررة وحلولها
- patterns أو workflows ثبتت فائدتها
- حقائق خاصة بالمشروع لا تظهر مباشرة من الملفات
- قيود البيئة أو الأمان أو الأداء

### ما لا يُحفظ

- النقاشات العابرة
- النتائج التي يمكن قراءتها مباشرة من الكود
- الفرضيات غير المثبتة
- المعلومات المتجاوزة
- أي شيء لا يفيد جلسة لاحقة

### ما لا يُحفظ أبداً

- أخطاء تحدث مرة واحدة ولا تمثل نمطاً
- معلومات متاحة في git log أو ملفات المشروع
- تفضيلات مؤقتة لجلسة واحدة
- معلومات عفا عليها الزمن (إصدارات قديمة، مكتبات لم تعد تستخدم)
- نجاحات متوقعة (الأمور التي سارت كما هو مخطط)

### قاعدة Plan vs Memory

- **إذا كان الشيء سيُنفَّذ في نفس الجلسة** → ضعه في خطة (Plan)، لا في الذاكرة
- **إذا كان الشيء سيفيد جلسات لاحقة** → احفظه في الذاكرة
- **إذا كان الشيء مؤقتاً بطبيعته** (حالة مهمة، تقدم عمل) → لا تحفظه. استخدم TaskCreate

### أنواع الذاكرة

- `user-preference`
- `project-fact`
- `architecture-decision`
- `workflow-pattern`
- `failure-pattern`
- `constraint`

### درجات الأهمية

- `permanent`
- `long-term`
- `temporary`
- `expires-soon`

### القاعدة العليا

عند تعارض الذاكرة مع الكود الحالي، **الكود الحالي هو المرجع الأعلى**.

### Schema

```json
{
  "project": "اسم المشروع أو النطاق",
  "type": "نوع الذاكرة",
  "importance": "permanent | long-term | temporary | expires-soon",
  "trigger": ["keywords"],
  "summary": "خلاصة قصيرة جدًا",
  "reason": "لماذا هذه الذاكرة مهمة",
  "source": "الجلسة أو السياق",
  "date": "YYYY-MM-DD",
  "status": "active | outdated | replaced"
}
```

### Workflow

**قبل المهمة:**

- `project-context` للمهمات الكبيرة أو الحساسة
- ثم `memory-search` بكلمات مرتبطة

**أثناء التنفيذ:**

- استخدم الذاكرة لتجنب التكرار لا لفرض افتراضات قديمة

**بعد المهمة:**

- خزّن فقط القرار أو workaround أو pattern الذي يستحق

### قواعد إضافية

- يُمنع تخزين الأسرار والمفاتيح والـ tokens
- `summary` قصيرة جدًا
- `trigger` عملية وقابلة للبحث
- التخزين الفعلي: ملفات `*.md` في `~/.claude/projects/*/memory/` (sqlite3 CLI غير متاح)
- التخزين المستهدف: `~/.claude/data/deepseek.db` (جدول `memories`)

### Feedback Memory Structure

عند حفظ memory من نوع `feedback` أو `failure-pattern`، استخدم هيكل:

- **Rule:** القاعدة أو النمط
- **Why:** لماذا هذا مهم — ماذا حدث عندما لم نتبعه
- **How:** كيف نطبقه في الجلسات القادمة

## 7) Quality Gates Policy

### القاعدة

لا تعتبر المهمة منتهية بمجرد اكتمال التنفيذ.
كل مهمة تمر على مستوى تحقق مناسب لحجمها.

### Hooks الحالية

- `block_dangerous.sh`
- `block_secrets.sh`
- `loop_prevention.sh`
- `auto_format.sh`

### مستويات التحقق

| المستوى          | حجم التغيير | الإجراء                                        |
| ---------------- | ----------- | ---------------------------------------------- |
| Basic            | صغير جدًا   | مراجعة ذاتية فقط                               |
| Quick Check      | متوسط       | تشغيل `quick-check`                            |
| Deep Review      | كبير        | تشغيل `deep-review`                            |
| Quality Pipeline | حساس        | تشغيل `code-quality-pipeline` أو `auto-verify` |

### متى تصبح إلزامية؟

- refactor كبير
- تعديل بنيوي
- تغييرات متعددة الملفات
- كود حساس أو أمني
- DB / Auth / API / Infra
- أي تغيير قد يكسر behavior قائم

### قاعدة الإيقاف

إذا فشل التحقق، يجب الإصلاح أولًا ثم إعادة التحقق.

## 8) Eval / Benchmark Policy

### الهدف

التحسن لا يُقاس بالشعور، بل بحالات ثابتة من شغلك الحقيقي.

### ابدأ تدريجيًا

ابن benchmark صغيرًا من:

- bug معقد
- refactor متوسط
- review
- migration
- تحليل مشروع

### معايير القياس

- صحة النتيجة
- الالتزام بالطلب
- عدد الأخطاء
- مقدار التعديل غير الضروري
- الوضوح
- السرعة
- الحاجة لإعادة العمل

### Eval Commands

مُدرجة في القواعد اليومية (CLAUDE.md) عند تغيير السياسات أو النماذج أو الـ workflows:

| الأمر            | الوظيفة                           |
| ---------------- | --------------------------------- |
| `compare-models` | مقارنة النماذج على benchmark ثابت |
| `eval-last`      | تقييم آخر مخرجات أو آخر تجربة     |

### قاعدة

- مستخدمة يوميًا عند تغيير السياسات — موثقة في CLAUDE.md و golden-set.
- الاستخدام المتخصص (دون تغيير سياسات) يبقى ضمن التقييم لا القواعد اليومية.

## 9) Priority Rules

عند التعارض، يكون ترتيب الأولوية:

1. طلب المستخدم الحالي
2. حالة الكود الحالية
3. سياسات الجودة
4. سياق المشروع
5. الذاكرة

### Conflict Resolution — ترتيب الأولوية بين ملفات النظام

عند تعارض الملفات الحاكمة:

1. **طلب المستخدم المباشر** — يسبق كل شيء
2. **CLAUDE.md** — التعليمات اليومية (الأقرب للمستخدم والأكثر تحديداً)
3. **OPS** — السياسة العامة (المرجع الكامل والتفصيلي)
4. **Golden Set** — الملخص السريع (للاسترشاد)
5. **Skills** — التعليمات الإجرائية (المنضبطة في سياقات محددة)
6. **الذاكرة** — المعلومات المسجلة من جلسات سابقة
7. **الافتراضات** — عندما لا ينطبق أي مما سبق

ملاحظة: التكرار المقصود بين CLAUDE.md و OPS مقبول — الأول مختصر والثاني مفصّل. عند التعارض، الأحدث زمنياً يسبق.

## 10) Failure Prevention Rules

- لا تبدأ التنفيذ قبل فهم كافٍ
- لا تستخدم أدوات ثقيلة لمهام بسيطة
- لا تخلط بين الاستكشاف والتنفيذ
- لا تحفظ في الذاكرة ما لا يفيد مستقبلًا
- لا تعتبر التعديل ناجحًا قبل التحقق
- لا تجعل كثرة الأدوات سببًا لبطء القرار

### لا تحسين بلا قياس

**القاعدة:** لا تُحسّن أداءً — ولا تشخّص بطئًا — قبل قياس رقم فعلي. ولا تحذف مكوّنًا لأنه «يبدو ثقيلًا».

**لماذا:** خطاف أمني بدا بطيئًا فنُسب البطء إلى استدعاء `node` لتحليل JSON. القياس أظهر أن `node` يكلّف ~90ms بينما التكلفة الحقيقية كانت **31 استدعاء `grep` منفصلًا** بـ~104ms لكل واحد. إزالة `node` كانت ستعيد ثغرة أمنية دون أن تحل شيئًا؛ دمج الأنماط في تمريرة واحدة خفض الزمن من ~1900ms إلى ~400ms.

**كيف تطبّقها:**

1. قِس أولًا (زمن قبل/بعد، عدد استدعاءات، حجم).
2. اعزل المصدر — لا تفترضه من شكل الكود.
3. أعد القياس بعد التغيير وأثبت الفرق برقم.
4. إن تعارض الأمان مع السرعة، حُلّ المشكلة الحقيقية بدل إسقاط الضابط الأمني.

## 11) Definition of Done & Ship Gate

### المبدأ

تُعتبر المهمة منتهية فقط إذا:

- تم فهم الطلب وتنفيذه بدقة
- تم استخدام النموذج المناسب
- تم استخدام الأداة المناسبة
- تم اجتياز بوابة التحقق المناسبة
- لم تبقَ آثار جانبية واضحة
- تم حفظ المعرفة المفيدة فقط إن وُجدت

### Ship Gate — فحص الجاهزية النهائية

انتهاء التنفيذ لا يعني الجاهزية للشحن تلقائيًا.

**لا يُغلق العمل** قبل المراجعة السريعة التالية (اختر حالة واحدة لكل بند):

| البند             | الحالة المختارة | الحالات الممكنة                |
| ----------------- | --------------- | ------------------------------ |
| Plan              |                 | تم / جزئي / غير مطلوب          |
| Build             |                 | تم / جزئي                      |
| Review            |                 | اجتاز / معلق / فشل / غير مطلوب |
| QA                |                 | اجتاز / معلق / فشل / غير مطلوب |
| Regression Risk   |                 | منخفض / متوسط / مرتفع          |
| Docs              |                 | محدّث / غير مطلوب / معلق       |
| Known Limitations |                 | لا يوجد / مذكورة               |

**قاعدة الإغلاق:** إذا كان هناك risk واضح أو جزء أساسي غير مُتحقق منه — لا تعتبر المهمة جاهزة للشحن.

## 12) Investigate Mode

### الهدف

عند وجود bug غير واضح أو behavior غير متوقع، لا يبدأ الإصلاح مباشرة.
يجب أولًا تشغيل مسار تحقيق منضبط يهدف إلى الوصول إلى root cause قبل أي تعديل.

### متى يُستخدم؟

- bug غير واضح السبب
- failure متكرر
- regression غير مفسَّر
- مشكلة يظهر لها أكثر من تفسير محتمل
- أي حالة يكون فيها الإصلاح التخميني عالي المخاطر

### القواعد

1. اجمع الأعراض أولًا.
2. حدّد فرضيات محتملة للسبب (2–3 كحد أقصى).
3. اختر فرضية واحدة فقط في كل مرة.
4. اختبر الفرضية باستخدام: `Grep` / `LSP` / تشغيل محلي / أو عزل الكود.
5. وثّق ما الذي تم نفيه وما الذي بقي محتملًا.
6. لا تبدأ fix قبل وجود فرضية مفسِّرة معقولة.
7. إذا فشلت 3 جولات تحقيق متتالية، أوقف المسار وغيّر طريقة التحقيق.

### المخرجات المطلوبة

- **symptom summary**: ملخص الأعراض
- **likely root cause**: السبب الجذري الأكثر احتمالًا
- **evidence**: الدليل على الفرضية الراجحة
- **rejected hypotheses**: ما تم نفيه ولماذا
- **recommended fix path**: مسار الإصلاح المقترح

### قاعدة

إذا لم تصل إلى root cause واضح بعد 3 جولات — أوقف وقدّم أدوات وسياقًا إضافيًا للمستخدم بدل التخمين.

## 13) QA Policy

### الهدف

التحقق لا يكون عامًا أو فضفاضًا، بل يركز على الأثر الفعلي للتغيير.

### الأنماط

- **qa-only**: فحص واكتشاف مشاكل بدون تعديل. استخدمه للـ review أو الـ audit.
- **qa**: فحص ثم إصلاحات بسيطة أو موجهة ثم إعادة تحقق.

### القاعدة الأساسية

يجب أن يكون QA مبنيًا على التغييرات الفعلية:

- الـ diff
- الملفات المتأثرة
- المسارات أو الـ flows المتأثرة
- acceptance criteria إن وُجدت

### متى يصبح QA مطلوبًا؟

- أي تغيير في UI
- أي flow للمستخدم
- أي bug fix مهم
- أي سلوك قد يسبب regression
- أي تغيير متعدد الملفات ينعكس على التجربة النهائية

### قواعد QA

1. اختبر ما تغيّر أولًا.
2. اختبر edge cases القريبة من التغيير.
3. بعد كل إصلاح، أعد التحقق.
4. أي bug تم إصلاحه يجب أن ينتج عنه regression check أو test إن أمكن.
5. إذا كان المطلوب report فقط — استخدم `qa-only`.

### مخرجات QA

- **areas tested**: المناطق التي تم اختبارها
- **issues found**: المشاكل المكتشفة
- **issues fixed**: المشاكل التي تم إصلاحها
- **retest status**: حالة إعادة الاختبار
- **remaining risks**: المخاطر المتبقية

> **العلاقة مع Quality Gates (Sec 7):** Quality Gates تحدد **كم** من التحقق (basic → deep-review).
> QA Policy تحدد **ماذا** تختبر. كلاهما قد يُطبَّق في نفس المهمة. مثلاً: مهمة "تعديل UI"
> تمر على **Quick Check** (Quality Gates) مع تركيز الاختبار على **التغيير في UI والـ flows** (QA Policy).

## 14) Handoff Pipeline

### الهدف

ربط المراحل ببعضها بدل تشغيل كل مرحلة بشكل منفصل.

### التسلسل الافتراضي

`plan → build → review → qa → ship`

### قاعدة الاستخدام حسب حجم المهمة

| الحجم | المثال                 | المسار المطلوب                      |
| ----- | ---------------------- | ----------------------------------- |
| صغير  | تعديل نص، fix بسيط     | `build → verify`                    |
| متوسط | feature جديدة محددة    | `plan → build → review`             |
| كبير  | feature متعددة الملفات | `plan → build → review → qa`        |
| حساس  | auth, payment, API, DB | `plan → build → review → qa → ship` |

### قواعد الـ handoff

1. كل مرحلة تُسلّم للمرحلة التالية **artifact أو summary** واضح.
2. لا تنتقل إلى `qa` قبل اكتمال `review`.
3. لا تنتقل إلى `ship` قبل اكتمال `qa`.
4. إذا كشفت مرحلة لاحقة مشكلة جوهرية — يعود المسار للمرحلة المناسبة، لا للبداية عشوائيًا.
5. إذا كانت المرحلة غير مطلوبة — تخطّها صراحةً، لا تتجاهلها بدون وعي.

### ربط مراحل Handoff بـ Quality Gates

| مرحلة Handoff | ما يقابلها في Quality Gates (Sec 7)         |
| ------------- | ------------------------------------------- |
| `verify`      | Basic (مراجعة ذاتية)                        |
| `review`      | Quick Check أو Deep Review (حسب الحجم)      |
| `qa`          | QA Policy (Sec 13) — مستقل عن Quality Gates |
| `ship`        | Ship Gate ضمن DoD (Sec 11)                  |

## 15) Search & Information Retrieval Policy

### الهدف

تحديد متى وكيف أبحث عن المعلومات، لتجنب المعلومات القديمة مع عدم إضاعة الوقت في بحث غير ضروري.

### Decision Boundary — متى أبحث؟

**مطلوب البحث عندما:**

1. **عتبة 10%**: إذا كان احتمال عدم دقة المعلومة > 10% — ابحث فوراً
2. **معلومات متغيرة**: أخبار، أسعار، قوانين، جداول، نتائج رياضية، شخصيات عامة
3. **منتجات وخدمات**: مواصفات، أسعار، توصيات قد تكلف المستخدم مالاً
4. **مكتبات برمجية**: إصدارات حديثة، breaking changes، API changes
5. **استشهادات**: إذا طلب المستخدم مصدراً أو اقتباساً دقيقاً
6. **تحقق**: إذا قال المستخدم "هل أنت متأكد؟" أو طلب التحقق
7. **مصطلح غير مألوف**: إذا كان المصطلح قد يكون خطأ إملائياً أو غير معروف

**ممنوع البحث عندما:**

1. محادثة عادية لا تحتاج معلومات حديثة
2. كتابة أو إعادة صياغة بدون احتياج بحث
3. ترجمة
4. تلخيص نقدمه المستخدم بالفعل
5. نصائح عامة غير معلوماتية
6. الرياضيات والمنطق والكود الخالص (بدون مكتبات خارجية)

### قواعد البحث

1. **Context7 أو MCP توثيق** مقدّم على البحث العام لمكتبات وأدوات البرمجة
2. **المصادر الرسمية** (documentation, papers) مقدّمة على المقالات والمنتديات
3. **التنوع**: استخدم مصادر من مجالات مختلفة عند الضرورة
4. **الجودة**: اعتمد على المصادر عالية السمعة، تجاهل المصادر غير الموثوقة
5. **إذا لم تجد إجابة**: لخّص ما وجدته ولماذا لم يكن كافياً
6. **خصص البحث**: اسأل سؤالاً محدداً، لا تبحث بشكل عشوائي

### مصادر البيانات المتخصصة

| المصدر       | الاستخدام                   |
| ------------ | --------------------------- |
| Context7     | توثيق مكتبات البرمجة        |
| Web search   | أخبار، معلومات عامة، منتجات |
| GitHub (MCP) | كود مفتوح، issues، PRs      |
| Supabase MCP | توثيق Supabase              |
| Vercel MCP   | توثيق Vercel                |
| Vision MCP   | تحليل الصور                 |
| Video MCP    | تحليل الفيديو               |

## 16) Citations & Attribution Policy

### الهدف

توحيد طريقة الاستشهاد بالمصادر لجعل الردود موثوقة وقابلة للتتبع.

### متى أستشهد؟

1. **أي معلومة ليست معرفة عامة** — يجب أن يكون لها مصدر
2. **المعلومات التي تغيرت محتمل > 10%** — استشهد بالمصدر الحديث
3. **إذا بحثت ولو مرة واحدة** — كل الحقائق المبنية على البحث تحتاج استشهاد
4. **الاقتباسات الحرفية** — ضع المصدر مباشرة بعد الاقتباس
5. **الأرقام والإحصائيات** — استشهد دائماً

### تنسيق الاستشهادات

```
【مصدر|اسم المصدر|URL】
```

أو للاستشهادات البسيطة داخل النص:

```
【اسم المصدر】
```

### قواعد التنسيق

- ضع الاستشهاد في نهاية الفقرة (أو inline للفقرات الطويلة)
- الاستشهاد بعد علامات الترقيم، ليس قبلها
- لا تضع الاستشهاد داخل **bold** أو _italic_ أو `code`
- لا تجمع كل الاستشهادات في نهاية الرد
- لا تضع سطراً كاملاً للاستشهادات فقط

### قواعد الجودة

1. **الصلة**: كل استشهاد يجب أن يدعم النص الذي يتبعه
2. **التنوع**: استخدم مصادر من مجالات مختلفة
3. **الدقة**: كل استشهاد يجب أن يعكس بدقة محتوى المصدر
4. **السمعة**: أكثر من نصف الاستشهادات من مصادر موثوقة
5. **الحياد**: إذا وجدت آراء متعارضة، استشهد بكل منها
6. **عدم التجاهل**: لا تتجاهل مصدراً وثيق الصلة ولو كان ضعيفاً

### قواعد الاقتباس

- لا تقتبس أكثر من 25 كلمة من مصدر غير غنائي
- الاقتباسات الغنائية: حد أقصى 10 كلمات
- لا تعيد إنتاج مقالات أو مقاطع محمية بحقوق النشر كاملة
- إذا طلب المستخدم اقتباساً، قدم مقتطفاً قصيراً ولخّص الباقي
